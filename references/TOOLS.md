# 외부 도구 선택 기록

아직 외부 MCP·플러그인·Skill을 설치하거나 연결하지 않았습니다.

| 도구 | 필요한 이유 | 공식 출처·라이선스 | 설치·버전 | 권한·필요 설정 | 실제 동작 확인 | 실패 시 대안 |
|---|---|---|---|---|---|---|
| 미선택 | 미정 | 미확인 | 미설치 | 미확인 | 미실행 | 미정 |

기존 개인 설정이나 인증값은 공개 저장소에 복사하지 않습니다. 프로젝트의 도구 허용 범위를 확인하고 필요한 도구만 선택합니다. 역할 파일을 clone한 것과 외부 도구 연결 완료를 구분합니다.

## 웹 서버와 브라우저 미리보기

서버 연결이 실패하면 아래 순서로 실패한 지점을 좁힙니다. 이 키트에는 실제 서비스가 없으므로, 이 절차만으로 특정 환경의 연결 성공이나 과거 오류 원인을 확정하지 않습니다. 실행한 결과는 `RUN.md`와 실제 검증 기록에 남깁니다.

### 1. 실행 방법과 서버 상태 확인

1. 실제 프로젝트의 README, `package.json` 등 실행 스크립트와 설정을 읽습니다. 이미 정해진 실행 방법을 우선 사용합니다.
2. 서버를 실행하고 준비 완료 메시지·오류·실제 포트를 확인합니다. 실행 명령을 입력한 것만으로 서버가 준비된 것은 아닙니다.
3. 플랫폼 미리보기에서 접근할 서버는 `0.0.0.0`에 바인딩합니다. 이는 서버가 연결을 받는 주소이며 Browser의 URL 칸에 입력할 접속 주소가 아닙니다.
4. 로그와 가능한 리슨 상태 확인 도구로 주소·포트를 확인합니다. Linux 환경에 `ss`가 있다면 별도 터미널에서 `ss -ltnp`를 사용할 수 있습니다. 도구가 없으면 로그·설정과 환경에 제공된 대안을 사용합니다.

`3000`은 예시입니다. Vite는 기본 포트가 다르고, 포트가 사용 중이면 다른 포트로 시작할 수 있습니다. 요청한 포트보다 **실제로 열린 포트**를 기준으로 연결합니다.

다음은 `package.json`의 `dev`가 해당 도구를 실행하는 경우에만 적용할 예시입니다. 프로젝트와 설치 버전을 먼저 확인합니다.

```sh
# dev가 Vite를 실행할 때. strictPort는 포트가 점유되면 다른 포트 대신 오류로 알립니다.
npm run dev -- --host 0.0.0.0 --port 3000 --strictPort

# dev가 Next.js의 next dev를 실행할 때
npm run dev -- --hostname 0.0.0.0 --port 3000
```

프로젝트에 없는 서버나 프레임워크를 이 예시에 맞추기 위해 추가하지 않습니다.

### 2. 서버용 터미널을 유지하고 내부 응답 확인

- 서버가 실행 중인 터미널은 닫지 않습니다. 선택 영역 없이 `Ctrl+C`를 누르면 실행 중인 서버가 중단될 수 있습니다.
- `+`로 새 터미널을 열어 검사 명령을 실행합니다. 일시적인 터미널 연결 문제는 ‘다시 연결’로 상태를 먼저 확인합니다.
- 터미널 입력에서 줄바꿈은 `Alt+Enter`(Mac `Option+Enter`), 붙여넣기는 Windows/Linux `Ctrl+Shift+V`(Mac `⌘V`)입니다. 텍스트 선택 후 `Ctrl+C`(Mac `⌘C`) 복사와 선택 영역 없는 명령 중단을 구분합니다.
- 같은 서버를 계속 새로 띄우지 않습니다. 재시작이 필요하면 본인이 띄운 서비스의 기존 상태를 확인하고 정상 종료·재시작합니다.
- RAM 16GB 같은 환경 한도를 고려해 필요한 프로세스만 유지합니다. 제출 전체 10GB 제한이라면 개별 파일이 아닌 합계로 확인하고, 불필요한 큰 산출물을 쌓지 않습니다. 실제 환경의 한도를 따릅니다.

실제 포트가 `3000`인 경우의 내부 확인 예시입니다. 다른 포트나 경로를 사용하면 바꿉니다.

```sh
curl -i --max-time 5 http://127.0.0.1:3000/
```

여기서 `127.0.0.1`은 **서버와 같은 작업 환경의 터미널**에서 요청하기 위한 주소입니다. Browser 접속 주소를 `127.0.0.1`로 바꾸라는 의미가 아닙니다. `curl`이 없다면 환경에 있는 HTTP 확인 도구를 사용합니다.

| 관찰 결과 | 다음 확인 |
|---|---|
| 연결 거부·시간 초과 | 프로세스 종료·시작 오류·실제 포트·리슨 주소 확인 |
| HTTP 404 | HTTP 응답은 도착했음. `/`가 실제 제공 경로인지 확인하고 필요한 페이지·API 경로로 재검사 |
| HTTP 500 | 서버가 응답했지만 처리 중 오류 발생. 해당 요청 시각의 서버 로그와 설정·입력을 확인 |
| 예상한 상태·내용 응답 | 내부 응답 확인을 기록하고 다음 단계의 플랫폼 Browser 확인 진행 |

HTTP 오류 응답을 포함해 명령 자체가 끝날 수 있으므로, 명령 종료 여부뿐 아니라 상태 코드와 응답 내용을 읽습니다. API 전용 서버의 `/`가 404인 경우에도 실제 API 경로를 별도로 확인합니다.

### 3. 플랫폼 Browser의 포트·경로 연결

1. 플랫폼 안의 Browser 도구를 엽니다.
2. **PORT**에는 실행 로그와 리슨 상태로 확인한 실제 포트를 입력합니다.
3. **URL 경로**에는 `/` 또는 `/dashboard` 같은 실제 경로를 입력합니다. 자동 표시된 호스트를 직접 조합하거나 `0.0.0.0`을 넣지 않습니다.
4. 원형 새로고침 버튼을 눌러 입력값을 적용합니다. 서버 재시작 후에도 포트가 달라졌는지 확인한 뒤 다시 연결합니다.
5. 화면이 열리면 사용자가 입력·버튼·이동 등 핵심 동작을 직접 확인합니다. 확인한 사람·동작·결과를 기록합니다.

‘해당 포트에 응답하는 서버가 없음’은 서버가 아직 준비되지 않았을 때도 표시될 수 있습니다. **터미널 오류·종료 여부 → 실제 포트 → `0.0.0.0` 바인딩 → 경로** 순서로 확인합니다. 내부 HTTP 성공은 미리보기 경유 연결이나 화면의 기능 성공을 보장하지 않습니다.

외부 터널을 만들거나 플랫폼의 감독·접속 설정을 변경하지 않습니다. 화면 안내대로 복구해도 계속 실패하면 발생 시각·입력 포트와 경로·내부 HTTP 결과·오류 문구를 환경의 문의 기능에 전달합니다. 키·토큰·비밀번호는 기록하지 않습니다.

### 4. 화면은 열리지만 일부 기능이 실패할 때

- **API 요청만 실패:** 실제 요청 URL과 서버 로그를 확인합니다. 브라우저 코드의 `http://localhost:다른포트`는 일반적으로 사용자의 PC를 가리킵니다. 기존 구조에 맞는 같은 출처의 상대 경로(`/api/...`), 앱 내부 프록시 또는 서버 측 호출을 검토합니다. 터미널에서 API가 열린 사실만으로 브라우저 요청도 성공한다고 단정하지 않습니다.
- **Vite의 명시적인 호스트 차단 오류:** 오류에 표시된 호스트와 플랫폼의 실제 미리보기 호스트를 대조합니다. 필요하면 설치 버전이 지원하는 앱 설정에서 신뢰할 정확한 호스트만 허용합니다. 근거 없이 `allowedHosts: true`나 CORS 전체 허용을 적용하지 않습니다.
- **화면·API는 동작하고 자동 새로고침만 실패:** 실시간 갱신 연결 오류와 서비스 자체의 실패를 구분해 기록합니다. 처음부터 플랫폼 연결 설정을 바꾸지 않습니다.

### 판단·검증 기록 예시 틀

아래는 결과를 채우기 위한 틀이며 실행 완료 기록이 아닙니다.

- 선택: 어떤 실행 명령·포트·연결 방식을 사용했는가?
- 근거: 프로젝트 설정과 관찰 결과 중 무엇을 근거로 선택했는가?
- 검증: 실행 명령, 기대한 상태·내용, 실제 관찰값, Browser 직접 확인 여부는 무엇인가?
- 한계: 확인하지 못한 경로·사용자 동작·플랫폼 연결 단계는 무엇이며 다음 확인은 무엇인가?

관련 공식 참고: [Vite 서버 설정](https://vite.dev/config/server-options), [Next.js CLI](https://nextjs.org/docs/app/api-reference/cli/next). 프레임워크의 현재 문서와 실제 설치 버전은 다를 수 있으므로 실행 옵션을 적용하기 전에 확인합니다.
