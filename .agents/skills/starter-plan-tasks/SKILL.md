# 작은 작업과 시간 계획

SPEC의 완료 기준, 기존 코드·실행 방법, 실제 남은 시간과 도구 사용 가능 여부를 먼저 확인한다.

1. 화면 하나·처리 하나처럼 구현부터 검증까지 끝낼 수 있는 작은 작업으로 나눈다. 각 작업에 목표, 수정 범위, 선행 작업, 완료를 확인할 방법을 붙인다.
2. 필수 기능을 먼저 정하고 선택 기능은 뒤로 둔다. 큰 구조 변경보다 현재 환경에서 실행 가능한 최소한의 결과를 우선한다.
3. 단독 진행, 역할을 나눠 순서대로 진행, 독립 작업 병렬 진행 중 현재 규모에 맞는 방식을 고른다. subagent 지원 여부뿐 아니라 인계·결과 취합·충돌 해결 비용도 이유에 포함한다.
4. 전체 마감과 실제 작업 시간 제한을 구분하고 응답 대기까지 포함해 구현·검증·문서·제출 시간을 배분한다. 현재 작업이 끝날 때마다 실제 소요와 남은 시간을 보고 계획을 조정한다.
5. 기존 PLAN에 작업·담당·순서·예상 시간·중요한 선택 이유를 기록한다. 병렬 작업은 수정 파일과 공유 데이터 형식을 먼저 나누고 통합 담당을 한 명 정한다.

계획만으로 실행 완료라 쓰지 않는다. 새로운 이슈 트래커나 외부 게시를 만들지 않고 승인된 첫 작업을 시작한다. 시간 배분의 예와 중단 기준은 저장소의 references/TIME_MANAGEMENT.md를 참고한다.

참고·각색 출처: Matt Pocock의 to-tickets. 외부 이슈 게시 대신 기존 PLAN을 사용한다. [출처와 라이선스](../THIRD_PARTY_NOTICES.md).
