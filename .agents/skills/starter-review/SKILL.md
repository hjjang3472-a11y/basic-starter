# 요구사항과 변경 코드를 검토하기

SPEC, PLAN의 선택 이유, 완료된 변경 내용과 실제 테스트 근거를 읽는다. 검토 범위를 먼저 정하고 아직 편집 중인 파일과 충돌하지 않는다.

1. 요구사항 충족 여부를 먼저 본다. 필수 기능 누락, 잘못 해석한 업무 규칙, 입력·출력 차이, 근거 없는 완료 주장을 확인한다.
2. 코드의 실제 위험을 확인한다. 해당 변경과 관련된 오류 처리, 권한, 데이터 손상·유출, 계산·상태·경계 조건, 중요한 성능 문제와 검증 누락을 살핀다.
3. 의심만으로 결함이라 단정하지 않는다. 파일·위치, 재현 조건, 기대와 실제, 사용자 영향과 근거를 연결한다. 관련 없는 스타일 변경이나 과도한 재설계를 요구하지 않는다.
4. 읽기 전용으로 “수정할 문제 / 영향·근거 / 제안하는 확인 방법”을 우선순위대로 보고한다. 명확한 문제가 없으면 검토 범위와 실행하지 않은 부분을 남긴다.

읽기만 한 검토와 실제 실행 검증을 구분한다. 직접 수정하거나 외부 이슈를 게시하지 않는다. 독립 검토자가 따로 필요하면 주 담당에게 요청하며 스스로 새 subagent를 만들지 않는다. 단독 진행에서는 자기 검토임을 표시하고 독립 검토라고 부르지 않는다.
